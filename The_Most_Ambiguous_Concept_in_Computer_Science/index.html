Computer architecture / Study guide

The Most Ambiguous Concept in Computer Science

The word “architecture” is thrown around everywhere in tech — but it quietly means different things in different rooms. This guide distills the excellent Core Dumped video into a clear, recall-friendly study path for developers who want to actually understand what ISA and Microarchitecture are, and why the difference matters every time you compile or run a program.

⏱ Too Long; Didn't Watch

“Architecture” is ambiguous because a hardware component (like an ALU or CPU) is only loosely defined. To remove the ambiguity we split it into two precise ideas: the Instruction Set Architecture (ISA) — the public contract software depends on — and the Microarchitecture — the secret internal wiring that implements it. One ISA can have many microarchitectures. Code compiled for an ISA runs on every microarchitecture that implements it, but not across different ISAs.

In one sentence
ISA = the rules; Microarchitecture = the wiring.
The analogy
ISA : Microarchitecture = Interface : Implementation = Algorithm : Code
Big-3 ISAs today
x86-64 (Intel/AMD) · ARM (Apple/phones) · RISC-V (open)
Why it bites you
An x86-64 binary won’t run on an ARM chip — wrong language.
Marketing trick
“New architecture!” usually = new microarchitecture, same ISA.
In software-land
When programmers say “architecture” they almost always mean the ISA.
01

“Architecture” Is a Slippery Word

▶ 0:00 The video opens by showing the word architecture repeated over and over in completely different contexts — CPU architecture, system architecture, software architecture, network architecture…

Each usage points at a slightly different idea. That fuzziness is the whole problem. Before this guide fixes it, the one thing to internalize is:

A term like “ALU” or “CPU” names what something does, but leaves almost every “how” undecided — the internal layout, the bit encodings, the widths, the supported operations. Two components can both be “a CPU” and be utterly different inside. That leftover freedom is architecture, and it’s exactly where the word gets ambiguous.

The rest of the page builds up the vocabulary to talk about that leftover freedom precisely.

02

From Sand to an ALU

▶ 0:27 A quick recap of the stack, because the ALU is where “architecture” first becomes interesting:

The hardware stack
  1. Transistors — tiny switches.
  2. Logic gates — AND, OR, NOT, XOR… built from transistors.
  3. Circuits — adders, decoders, multiplexers… built from gates.
  4. Special-purpose units — e.g. an adder-only circuit.
  5. General-purpose units — combine many circuits, pick behaviour with an input.
Why general-purpose matters

A circuit that does one thing is just hardware. A circuit that can do several things based on an opcode input is the seed of a whole computer. The ALU is the canonical example — and the perfect toy model for the rest of this guide.

The ALU: our running example

An Arithmetic Logic Unit (ALU) takes two data inputs and an opcode, and produces one output. The opcode is a small bundle of bits that selects which operation runs.

Two data in, one opcode in, one result out. That’s the entire external interface — and notice it says nothing about what’s inside the box. Hold that thought.

03

“Implementation” — The Bridge Idea

▶ 1:27 To connect hardware to something developers already intuit, the video borrows a software word: implementation.

In software, one problem has many correct algorithms — we call each an implementation.

In hardware, one component has many correct internal designs — we call each an architecture.
Architecture is to hardware what an algorithm is to software.

The video illustrates this with three different C programs that all find the maximum value in an array. Same answer, three completely different strategies. This is the exact same situation as “one ALU, many internal designs.”

Approach 1 · Iterative

Scan left→right, keep the largest so far.

// one pass, O(n)
int find_max(int a[], int n) {
  int m = a[0];
  for (int i=1; i<n; i++)
    if (a[i] > m) m = a[i];
  return m;
}
Approach 2 · Recursive

Max of rest, then compare last element.

// divide & conquer
int find_max(int a[], int n) {
  if (n == 1) return a[0];
  int r = find_max(a, n-1);
  return a[n-1] > r ? a[n-1] : r;
}
Approach 3 · Sort

Sort ascending, return last element.

// correct, but wasteful
int find_max(int a[], int n) {
  sort(a, n);   // O(n log n)
  return a[n-1];
}

All three return the same value for the same input — just like three ALU designs that produce the same output. The choice of strategy is an implementation detail… until it isn’t.

04

How Do You Even Build an ALU? (And Why It Breaks Compatibility)

▶ 2:28 The simplest recipe: build a separate circuit for each operation, then use a binary decoder to switch the right one on based on the opcode.

The 2-bit opcode table shown in the video

Opcode (2 bits)OperationExample
00Addition1010 + 0011 = 1101  (10 + 3 = 13)
01Subtraction1010 − 0011 = 0111  (10 − 3 = 7)
10Bitwise AND1010 & 0011 = 0010  (10 & 3 = 2)
11Bitwise OR1010 | 0011 = 1011  (10 | 3 = 11)

A 3-bit opcode scales this to 8 operations (add, sub, mul, div, NOT, AND, OR, XOR) — the video shows 0110 OR 0010 = 0110 using opcode 110.

The decoder routes the opcode

A binary decoder turns n opcode bits into 2ⁿ enable lines — exactly one of which goes high. That single hot line selects which operation’s result reaches the output.

Here’s the trap: the bit pattern 01 is a choice. One designer might encode 01=subtract; another might encode 01=multiply. Feed the same bits to both ALUs and you get completely different results. They are both “ALUs,” but they speak different languages.

So “different architecture” can mean “incompatible” — but, as the next section shows, it doesn’t have to.

05

Same Output, Three Totally Different Insides

▶ 6:38 The video’s pivotal moment: you can wire an ALU three fundamentally different ways and still get bit-identical results. They are different architectures but compatible.

Design A · Output selection
  • Inputs reach all units at once
  • Every operation computes simultaneously
  • A selector (MUX) picks one result to output

Wasteful but dead simple.

Design B · Input routing
  • A bus router sends inputs to only the active unit
  • Idle units never see the data
  • Output is taken straight from the active unit

Routing lives at the entrance.

Design C · Enable / activation
  • Inputs reach all units
  • Decoder activates only one unit (others sit idle)
  • Only the active unit produces a real result

Selection via an enable pin.

From the outside — same inputs, same opcode, same output. From the inside — three unrelated circuits. They are different microarchitectures implementing one identical ISA. This is the precise, non-ambiguous statement we’ve been building toward.

06

The Fix: ISA vs. Microarchitecture

▶ 7:44 To kill the ambiguity, split “computer architecture” into two precise layers. When people say “computer architecture” loosely, they usually mean both together.

ISA · Instruction Set Architecture

The public contract

The programmer-visible rules between software and the processor: which instructions exist, how they’re encoded into bits, their formats, registers, data types, addressing modes, and privilege levels.

Think of it as “the language + grammar the CPU speaks.” Software depends on it; it must not change silently.

Video’s framing: the externally-visible rules — what inputs exist, what each opcode means, what output to produce.

Microarchitecture

The secret wiring

The internal circuitry and organisation that makes a processor actually behave as the ISA demands — pipelines, caches, predictors, execution units, the ALU design.

Think of it as “how the sausage is made.” Programmers (usually) don’t see it; engineers optimise it.

Video’s framing: the three different internal ALU designs — all obeying the same external rules.

One ISA → many microarchitectures. A program compiled for an ISA runs on any microarchitecture that correctly implements it — but not on a chip with a different ISA.

What an ISA actually specifies (the video’s checklist)

This is why the ISA is a thick rulebook, not a single sentence. The video flashes a sprawling catalogue. Categories include:

Instruction set

Instruction names & opcodes · encoding formats & lengths · fixed vs variable length · prefixes/suffixes · operand count & order · immediate encodings · alignment · illegal/reserved encodings · optional extensions

Registers

Number & names of GPRs · widths · program counter · stack/frame pointers · status/condition flags · system & control registers · FP & vector/SIMD registers · aliases · privilege-level access

Behaviour

Arithmetic (signed/unsigned, overflow, carry, saturation) · bitwise (shifts, rotates, popcount) · data types & sizes · comparison & condition flags · addressing modes · memory ordering

The one-paragraph effect

For any task, the ISA dictates which small operations you’re allowed to combine and how they must be translated into binary so a CPU can receive, decode, and execute them. It is an abstract specification — a list of promises the hardware makes to the software.

Every box above is a distinct microarchitecture — yet a single x86-64 binary runs on all of them. That’s ISA compatibility in action.

That same x86-64 binary will not run on an ARM chip (e.g. Apple’s M-series). The bits mean different things to a different ISA. To run there, the program must be recompiled (or rewritten) for ARM.

“New architecture!” usually means new microarchitecture

▶ 11:30 When Intel/AMD/Apple announce “a brand-new architecture,” they almost always mean a new microarchitecture for an existing ISA. Shipping a genuinely new ISA every year would be commercial suicide — every existing program would need recompiling or rewriting.

In June 2020, Apple announced it would move the Mac from Intel’s x86-64 to its own ARM-based Apple silicon — completing the switch by mid-2023. Because the ISA changed, every app had to be recompiled for ARM. Apple bridged the gap with:

  • Universal 2 binaries — contain both x86-64 and ARM64 code.
  • Rosetta 2 — translates x86-64 instructions to ARM64 on the fly so old apps keep working.

A textbook case of the video’s thesis: same high-level source, different ISA, mandatory recompile.

08

Deep Dive: RISC vs CISC, Made Tangible

The video names x86-64, ARM, and RISC-V but doesn’t dwell on why they differ. This section adds the missing vocabulary developers need.

ISAs are loosely grouped into two design philosophies. The split that matters most in practice:

RISC (ARM, RISC-V, MIPS, PowerPC…)CISC (x86, VAX, PDP-11…)
Memory accessLoad/store — only load/store touch memory; ALU ops use registers onlyMemory operands allowed inside most instructions
Instruction lengthFixed (e.g. 32 bits)Variable (x86: 1–15 bytes)
Instruction countFew, simple, often single-cycleMany, complex, often multi-cycle
RegistersMany (ARM64: 31 GPRs)Fewer (x86-64: 16 GPRs)
Addressing modesFewMany

The difference you can see: one line of C, two very different programs

The video closes on the high-level statement count = count + 1; being identical across architectures. Here’s what a compiler actually emits for it — and it reveals the load/store rule in action.

x86-64· CISC · register-memory · 1 instruction
; count = count + 1;   (count is a global int)
; x86-64 lets ALU ops address memory directly:
    inc DWORD PTR [rip + count]

; one instruction: read, add 1, write — all implicit

The CISC ISA folds “load → modify → store” into a single instruction with a memory operand.

ARM64 / AArch64· RISC · load/store · 5 instructions
; count = count + 1;   (count is a global int)
; ARM64 ALU ops CANNOT touch memory.
    adrp  x0, count            ; page address of count
    add   x0, x0, :lo12:count  ; full address
    ldr   w1, [x0]            ; load  → register
    add   w1, w1, #1         ; modify (register only)
    str   w1, [x0]            ; store ← register

The RISC ISA forbids memory operands in arithmetic — so the compiler emits explicit load/modify/store steps.

On a load/store ISA (ARM, RISC-V), only load and store instructions may touch memory. Everything else works on registers. On x86-64, most instructions can read/write memory as part of the operation. Same C line, very different machine code — because the ISA differs, not just the microarchitecture.

A well-cited 2013 study (Power Struggles, HPCA) measured real ARM and x86 hardware and concluded the ISA being RISC or CISC is “largely irrelevant” to modern performance and energy — what dominates is the microarchitecture (pipelines, caches, predictors). Modern x86 chips even decode CISC instructions into internal RISC-like “micro-ops.” This is exactly the video’s deeper point: the ISA decides compatibility; the microarchitecture decides speed.

09

Why Everyone Dreaded “Porting” in the 1980s

▶ 11:58 The video closes its historical loop with a clip about how painful it was to move software between machines when every computer had a different architecture — including absurdly varied word sizes.

The word-size chaos of the era

MachineYearWord size
DEC PDP-8196512-bit
IBM System/360196432-bit
DEC PDP-6 / PDP-101964 / 196636-bit (not a power of two!)
CDC 6600196360-bit
DEC PDP-11197016-bit
1960s–70s
Each vendor’s machine had its own ISA, word length, and quirks. Software written in assembly for one box was useless on another — the OS literally “had to be rewritten for each computer architecture.”
1972
Dennis Ritchie creates C at Bell Labs (for Unix on the 16-bit PDP-11). A high-level language could be recompiled per ISA instead of hand-rewritten in assembly — the first big escape hatch from architecture lock-in.
1980s
Porting is still painful (C wasn’t perfectly portable; word sizes & signedness bit everyone), but high-level languages + compilers make it survivable. The industry converges toward a few dominant ISAs.
Today
A handful of ISAs (x86-64, ARM, RISC-V) dominate. You almost never hand-write assembly; compilers target each ISA for you. “Architecture” for a programmer now almost always means the ISA — because that’s the layer that decides whether your compiled program will run.

Because the ISA is the layer software interacts with — it determines how programs must be written, compiled, and executed — when programmers say “architecture,” they almost always mean the ISA. The microarchitecture is an engineering concern hidden beneath it.

10

The Mental Model, Compressed

“Architecture” is ambiguous on purpose — terms like ALU/CPU define what, not how, leaving freedom that designers fill differently.
Split it in two: ISA = the public contract software depends on; Microarchitecture = the internal wiring that fulfils it.
One ISA → many microarchitectures. Three ALU designs can be unrelated inside yet produce identical outputs — different micro, same ISA, fully compatible.
Compatibility follows the ISA, not the silicon. An x86-64 binary runs on any Intel/AMD microarchitecture; it does not run on ARM.
“New architecture” ≠ new ISA. Vendor launches are usually new microarchitectures — preserving the ISA keeps existing software working.
For programmers, “architecture” ≈ ISA. It’s the layer that decides how your code is compiled and whether it will run.
RISC vs CISC is a real distinction (load/store, fixed vs variable length), but modern performance is dominated by microarchitecture, not the ISA label.
Quick recall · ISA
  • The language & rules
  • Decides compatibility
  • Examples: x86-64, ARM, RISC-V
  • Changes rarely (breaks software)
Quick recall · Microarchitecture
  • The wiring & implementation
  • Decides speed/efficiency
  • Examples: Zen 5, Raptor Lake, Apple M4
  • Changes every generation
11

Check Your Recall

Try to answer first, then reveal. (These test the ideas, not trivia.)

Q1.You compile a program for x86-64. Will it run natively on an Apple M4 chip? Why or why not?
No. The M4 implements the ARM ISA, not x86-64. The same bit patterns mean different things under a different ISA, so the binary won’t run — it must be recompiled (or translated, e.g. via Rosetta 2).
Q2.Two CPUs have completely different internal circuitry but run the same binaries. Which layer is identical, and which differs?
Identical ISA; different microarchitecture. Same public contract → same binaries; the internal wiring (pipelines, caches, execution units) is the designer’s private choice.
Q3.A vendor announces “a brand-new CPU architecture!” What is it most likely to actually be?
Almost certainly a new microarchitecture implementing an existing ISA (e.g. a new Zen or Lake core). A genuinely new ISA would force everyone to recompile or rewrite their software.
Q4.Why does count = count + 1; compile to one instruction on x86-64 but several on ARM64?
x86-64 (CISC) lets arithmetic instructions use memory operands (inc DWORD PTR [count]). ARM64 (RISC) is load/store: only ldr/str touch memory, so the compiler must explicitly load → add → store.
Q5.What single sentence captures the relationship between ISA and microarchitecture?
The ISA defines the rules the hardware must obey; the microarchitecture is one specific way of obeying them. One ISA can have many microarchitectures.
12

Glossary

ALU Arithmetic Logic Unit
A combinational circuit that performs arithmetic and bitwise operations on integer binary inputs, selected by an opcode. The video’s running model for “architecture.”
ISA Instruction Set Architecture
The programmer-visible contract between software and a processor: the instructions, their binary encodings, registers, data types, and addressing modes.
Microarchitecture a.k.a. computer organization
The internal circuitry and organisation that implements a given ISA. One ISA can have many microarchitectures (e.g. Zen 5, Raptor Lake).
Opcode
A small bundle of bits (part of an instruction) that selects which operation a circuit (like an ALU) performs.
Binary decoder
A circuit that turns n input bits into 2ⁿ output lines, exactly one of which is active. Used to route an opcode to the correct operation.
Implementation
One specific way of realising a component or solving a problem. In software = an algorithm; in hardware = an architecture/microarchitecture.
Compatibility
Two pieces of hardware are compatible if the same inputs (instructions/bits) produce the same outputs — i.e. they share the same ISA.
x86-64 a.k.a. AMD64
The dominant CISC ISA for desktop/laptop/server CPUs; implemented by Intel and AMD microarchitectures.
ARM / ARM64 / AArch64
A RISC ISA family used in phones, tablets, Apple Silicon, and increasingly servers. Apple M-series chips implement ARM64.
RISC-V
An open, royalty-free RISC ISA used in research, embedded systems, and custom silicon.
RISC Reduced Instruction Set Computer
An ISA philosophy: simple, fixed-length, single-cycle instructions; load/store memory model; many registers. (ARM, RISC-V, MIPS.)
CISC Complex Instruction Set Computer
An ISA philosophy: richer, variable-length instructions that can operate directly on memory; fewer registers. (x86, VAX, PDP-11.)
Load/store architecture
An ISA where only load and store instructions access memory; all arithmetic works on registers. Characteristic of RISC ISAs.
Register
A small, fast storage location inside the CPU. The ISA defines how many exist, their names, widths, and uses.
Word size
The native unit of data a processor handles. Historically chaotic (12, 36, 60-bit…), now mostly standardised at 32/64-bit.
Compile
Translate source code into the binary instructions of a specific ISA. Recompiling is required when targeting a different ISA.
Rosetta 2
Apple’s translation layer that runs x86-64 binaries on ARM64 Apple Silicon by translating instructions at runtime.
